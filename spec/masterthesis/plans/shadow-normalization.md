# Motivation
≈ is a trace monoid: distinct labels commute, equal labels keep their order AND their multiplicity. The multiplicity is inherited from scoped labels (Leijen, P&X), where it is observable through restriction `ρ \ l`. MiniNix has no restriction, and Nix's `//` on attribute sets drops an overwritten key, so a shadowed field (an l-field with an earlier l-field to its left, across variables too) is never observable: not by lookup, not after substitution, not after concatenation.

Keeping it costs the most common Nix idiom, `defaults // overrides`, whenever an overridden record meets a plain one at a monomorphic position. Run in Lean (scratchpad `DeadFields2.lean`, base = `{name = ""; v = 0;}`):

| program | runF |
|---|---|
| `[ base (base // {name = "";}) ]` | clash |
| `(f: {a = f base; b = f (base // {…});}) (r: r.v)` | clash |
| same with let-bound `f` | `{a: int \| b: int}` |
| `[ (base // {…}) (base // {…}) ]` | `[{name: string \| v: int \| name: string}]` |

Option C (unification modulo the observational relation) is excluded. That relation is a partially commutative regular band: on rows, where the left wins, ρ | ρ ≡ ρ and ρ₁ | ρ₂ | ρ₁ ≡ ρ₁ | ρ₂ (left-regular); in Nix syntax, where the right wins, x // x = x and x // y // x = y // x (right-regular). Idempotent, hence not cancellative, and every forced move of ≐ᵣ rests on cancellation. Already `(l: Int | α) ≐ (l: Int)` loses its mgu (α ≔ ε vs α ≔ (l: τ)). C is new research and conflicts with G4 (efficiency).


# Goal
- The unifier ignores shadowed fields by normalizing its input. Its rules and its metatheory stay untouched
- The declarative system identifies a row with its normal form, so inference stays sound
- The four programs above: the two clashes type as `[{name: string | v: int}]` and `{a: int | b: int}`
- Thesis split: ≈ is the algebra unification works in (trace monoid), ≡ is what the program means


# Non-goals
- No change to the cascade or to anything in `lean/RowUnify/` beyond a call site
- No unification modulo ≡ (Option C)
- No removal of duplicate row variables (`(α | α) ≡ α` holds semantically, but nf keeps both; see Open questions)
- No normalization in the middle of a unification run (see D3)
- No restriction / `removeAttrs`


# Design

## D1 Normal form
`nf : Row → Row`, `nfTy : Ty → Ty`, on spines: walk left to right with the set L of labels seen so far; drop `l: τ` if l ∈ L, otherwise keep it, add l to L, and normalize τ. Variables and keyed fields are kept; a keyed field `${κ}: τ` is NOT treated as an occurrence of any label (its label is unknown) and is never dropped.
- `nf` is idempotent, `ftv (nf ρ) ⊆ ftv ρ`, size does not grow
- deep: `nfTy` recurses into record rows, arrows, lists

## D2 Declarative relation ≡
≈ stays exactly as it is (trace monoid, `rowEquiv_iff_char`). New relation ≡, the congruence generated by ≈ and one axiom:

    ≡-shadow:   l ∈ labels(ρ)   ⟹   (ρ | l: τ) ≡ ρ

with labels(ρ) the literal field labels of ρ's spine (keyed fields do not count).
- `≡` is used by T-eq and by ≼ (≈ then ⊑) instead of ≈
- Characterization: `ρ₁ ≡ ρ₂ ↔ nf ρ₁ ≈ nf ρ₂` (types: `nfTy τ₁ ≈ nfTy τ₂`)
- Needs: `ρ ≈ ρ' → nf ρ ≈ nf ρ'` (commuting distinct labels within a segment does not change which l-field comes first); `ρ ≡ nf ρ`
- Lookup respects ≡ (the dropped field is never reached; lookup stops at the earlier l-field or at a variable before it)
- ≡ is stable under substitution (substitution adds fields, never removes the earlier l-field)

## D3 Unification entry
The only algorithmic change: `SolveTy` / `SolveRow` (`Infer.lean` ~375) apply the substitution and then `nfTy` / `nf` before calling `unifyTyF` / `unifySpineMF`. The unifier itself is unchanged.
- All unification theorems hold verbatim for the normalized problem
- Success: θ(nf ρ₁) ≈ θ(nf ρ₂), hence θρ₁ ≡ θρ₂ (≈ ⊆ ≡, ≡ stable under θ, ρ ≡ nf ρ)
- Clash / occurs now mean: no ≈-unifier of the normalized problem. Not: no ≡-unifier. Example: `(α | l: Int) ≐ (l: Bool)` clashes, but α ≔ (l: Bool) is a ≡-unifier (the l: Int becomes shadowed under θ)
- Shadowed fields that appear mid-run (a payload binding lands in the residual spine via `sApplySubst`) are not normalized. They are compared under ≈: sound, possibly a clash. Normalizing there would break `unifyRowM_success_mgu`

## D4 Inference
- `SolveTy.unifies` and friends: conclude ≡ instead of ≈ for the applied types
- `inferSound` / `runSound`: wherever a unifier fact is consumed, route through ≈ ⊆ ≡
- Stumps: D-hit pins `θδ ≈ τ`. Switch to ≡ (lookup respects ≡, so the verdict does not change). Check `LetSpent` and the fillability condition, which compare results syntactically
- Reported types: apply `nfTy` to `τ⟦S′⟧` for display (cosmetic, optional)

## D5 Type safety
- qPreservation: T-eq case is generic; record cases go through `lookup_equiv` (`Qualified.lean:951`, 1458ff), to be replaced by the ≡ version
- `hasSing` invariance under ≈ (`Qualified.lean:2526`): check it under ≡-shadow (both sides keep at least one field, so expected to hold)
- Run time is unchanged: E-conc keeps duplicates, selection never reaches them

# Risks
- R1 D-hit / LetSpent / fillability compare result types; switching to ≡ may touch more of `LetSound.lean` / `Finalization.lean` than expected
- R2 Precision ≼ transitivity (`minimal.lean` ~2777) is proven for ≈ then ⊑; needs redoing for ≡ then ⊑ (commutation of ≡ past ⊑)
- R3 Keyed fields: a keyed field may later become l and shadow a following l-field. nf must not drop anything because of a keyed field, and ≡-shadow must not count keyed fields. A keyed field BEFORE a literal l-field does not make that l-field shadowed
- R4 Principality statements (`selQ_principal`) are stated with ≼; they should survive with ≡, but check
- R5 Proof size of `nf_respects_equiv` over the ≈ derivation (assoc/units/comm cases); fallback: prove it via `Row.Char`
