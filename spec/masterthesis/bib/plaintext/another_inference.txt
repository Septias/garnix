Another Type Inference Algorithm for First-Class Implicit
Polymorphism
J. GARRETT MORRIS, The University of Iowa, USA
We propose yet another approach to type inference with first-class implicit polymorphism, based on the
interleaving of an Algorithm M-style constraint-generating elaboration of terms and a solver for the generated
constraints. The novelty of our approach is that types include explicit syntactic representations of unknown
polymorphic types during type inference. Solving unification constraints with unknown polymorphic types
also computes type arguments for the elaborated terms. The resulting system is uniform, simple, extends to
support domain-specific constraints, and compares favorably with other approaches to first-class implicit
polymorphism.

1   Introduction
Implicit polymorphism has been a hallmark of typed functional programming since the introduction
of Hindley-Milner type inference [17]. It has proved expressive, understandable to programmers,
easy to implement, and amenable to a variety of extensions, from type classes [29] and type families
[24], to variant subtyping [5], to generalized algebraic data types [22], to many many more.
   At the heart of Hindley-Milner type inference is a compromise in the treatment of polymorphic
types. Quantifiers can appear at the outside of types—∀a.a → a is the type of the identity function—
but not inside types—the type of self-application, (∀a.a → a) → (∀a.a → a), is not allowed. This
restriction makes it possible for type inference to be sound and complete, but comes at a significant
cost in expressiveness. There have been many proposals to relax this restriction, making implicit
polymorphism closer to first class, each with its own tradeoffs. Some are highly expressive, but at
the cost of new programmer-visible features of the type system. Others are highly localized in their
implementation, but introduce more restrictions on where and how polymorphism can be used.
   Our interest in first-class implicit polymorphism arose from its interaction with qualified types.
Qualified types add domain-specific constraints to typing and type inference, and can capture ideas
from type classes [8] to row types [6, 20] to first-class polymorphism itself [16]. Many approaches
to first-class polymorphism use the type information computed during type inference to guide the
introduction of implicit type abstractions and implicit type applications. Domain-specific constraint
solving may reveal polymorphic types (seemingly) too late to introduce implicit type applications.
This causes a significant loss in the expressiveness of first-class polymorphism.

   We propose Another Type Inference Algorithm (ATIA) for first-class implicit polymorphism.
While inspired by qualified types, our approach is independent of that application. ATIA consists
of the interleaving of an Algorithm M-style constraint-generating traversal of terms and a simpli-
fication algorithm for the generated constraints. Its traversal pushes expected type information
towards the leaves of the term, rather than returning inferred type information towards the root.
This is naturally suited to first-class implicit polymorphism, as we will use expected types to guide
the introduction of implicit polymorphism. The novelty of our approach is that we extend the
syntax of types with an explicit representation of (both explicit and implicit) type instantiation, but
only during type inference. Type instantiations never appear in the final computed types. Solving
unification constraints involving implicit instantiations also computes the type arguments that
need to appear in the elaborated term. ATIA requires small and routine extensions to traversal,
is modular in its constraint solving algorithm, and is competitive with the state of the art in type
inference for first-class implicit polymorphism.
   The paper proceeds as follows. We begin with an overview of first-class implicit polymorphism
and our approach to type inference (§2). We introduce a small language with first-class implicit
polymorphism (§3), and describe the traversal (§4) and constraint solving (§5) portions of ATIA.
We give two examples of ATIA and its extension (§6). We sketch ATIA’s metatheory (§7), describe
our (experimental) implementation (§8) and compare it to a collection of benchmarks of first-class
implicit polymorphism (§9). We conclude by discussing related (§10) and future (§11) work.

2     Overview
2.1     The Problems of Implicit Polymorphism
The problem of implicit polymorphism is to, given a term in a language with implicit polymorphism,
produce a type-correct elaboration of that term in which all implicit polymorphism is made explicit.
The elaboration may be in a subset of the original language, such as in a setting with dependent
types, or may be in a different language, such as elaborating Haskell programs to programs in
System FC. Following Kovács [11], we divide this into two problems, abstraction insertion and
application insertion. Abstraction insertion is the problem of discovering which terms should be
surrounded with implicit type abstractions, and application insertion is discovering which terms
should be followed by implicit type application.
   Consider the term auto (λx.x) true, where auto : (∀a.a → a) → (∀a.a → a) is self-appliction,
and true : Bool is a Boolean constant. One elaboration of this term is to auto (Λt.λx:t.x) [Bool] true
(where we write explicit type abstraction with Λ and explicit type application with [−]). In producing
this elaboration, we have inserted a type abstraction surrounding λx.x, giving a valid argument to
auto. We have inserted a type application following auto(λx.x), as its result (of type ∀a.a → a)
must be instantiated to apply to a Boolean argument.
   Hindley-Milner type inference gives a purely syntactic solution to these problems: type ab-
stractions are introduced at let-bindings, and type applications are introduced at variables. MLF
allows arbitrary insertion of type abstractions and type applications, but must extend quantification
with an instantiation relation. Most other solutions use some combination of syntactic restriction
and type information. QuickLook [25], for instance, can be summarized in part as allowing type
applications anywhere in application spines, guided by the types of the terms at their heads.

2.2     Implicit Polymorphism and Constraints
Our interest in this problem arose from the intersection of first-class implicit polymorphism and
qualified types. The former requires type inference to discover the need for implicit type arguments,
typically by observing that a term has polymorphic type but appears in a context which does not

supply type arguments. The latter introduces a distinct constraint solving step to type inference,
which may refine metavariables introduced during type inference. In combination, then, constraint
solving may lead to polymorphism appearing in terms after the initial type inference pass, and so
not triggering implicit argument insertion.
   To make this problem concrete, we describe a specific example we countered in implementing
type inference for Rω [7]. Rω is an extension of Fω with qualified types and row types. A row type
is an association of labels (type-level immmutable strings) to types or type constructors, written
{ℓ1 ⊲ τ1 . . . ℓn ⊲ τn }. Rows are used to describe the fields of record types and the constructors of
variant types. Rω has several constraints on rows, which appear in qualified types. For example,
the constraint ρ 1 ≲ ρ 2 is satisfied if every association ℓ ⊲ τ appearing in ρ 1 also appears in ρ 2 .
   In this setting, we encountered the term sel d k f x with expected type T υ, in which: sel :
∀l t z.{l ⊲ t} ≲ z ⇒ Record z → Sing l → t is the polymorphic field selection function for records;
d : Record ρ is some record; k : Sing ℓ is a singleton corresponding to field ℓ; f : τ → υ is a function;
and, x : T τ is a value. Why we encountered this particular term is unimportant here. Inferring a
type for this term requires finding suitable instantiations for the type variables l, t, and z in the
type of sel. The natural solutions are ρ for z, ℓ for l, and (τ → υ) → T τ → T υ for t, and so type
inference produces the elaborated term sel [ρ] [ℓ] [(τ → υ) → T τ → T υ] d k f x and emits the
constraint {ℓ ⊲ (τ → υ) → T τ → T υ} ≲ ρ. (There is also an implicit argument to sel for the
solution of this constraint; we have omitted it as it is not relevant to the current problem.)
   Unfortunately, the emitted constraint is not satisfiable and so type inference for this term will fail.
The corresponding entry of ρ is ℓ ⊲ ∀ab.(a → b) → T a → T b, and the types (τ → υ) → T τ → T υ
and ∀ab.(a → b) → T a → T b do not unify. It is not the case, however, the that initial term
was necessarily ill-typed, just that the natural introduction of implicit arguments was insufficient.
The correct elaboration of this term is sel [ρ] [ℓ] [∀ab.(a → b) → T a → T b] d k [τ] [υ] f x, with
emitted constraint {ℓ ⊲ ∀ab.(a → b) → T a → T b} ≲ ρ. This constraint is satisfiable, and so
type inference succeeds. This example raises two questions: how was type inference to know
that implicit arguments were needed after k, and how should the need to solve those implicits be
conveyed to constraint solving? We emphasize that the row ρ is not necessarily known in advance:
ρ itself might be a metavariable, capturing the type of some other complex expression. Interleaving
type inference and constraint solving, hoping to surface polymorphism sooner, is not a scalable
solution.

2.3   Our Approach
ATIA combines an Algorithm M-style traversal of terms, producing elaborated terms and a set of
constraints (unification and otherwise), and a solver for the generated constraints. We extend the
grammar of types, only as they appear during constraint generation and constraint solving, to capture
potential implicit polymorphism, and extend unification to resolve potential implicit polymorphism.
The resulting algorithm is expressive, modular, and relatively simple to implement.
   Algorithm M, named and formalized by Lee and Yi [13], is Milner’s Algorithm W turned upside
down. Like Algorithm W, it is a (single) traversal of the input term, computing (if possible) a typing
of the input term and corresponding elaboration. In Algorithm W, the inferred type of a term is a
result of the algorithm, and so unification is typically performed at interior nodes of the syntax
tree. In Algorithm M, the expected type of a term is an input to the algorithm, and so unification
is typically performed at leaves of the syntax tree.
   There are multiple reasons to prefer Algorithm M. Lee and Yi show that Algorithm M stops
earlier than Algorithm W does—that is to say, closer to the leaves of the syntax tree—and thus more
tightly identifies type errors. In the context of first-class implicit polymorphism, Algorithm M
can push polymorphic types from functions to their arguments, improving the typing of those

arguments. However, Algorithm M might seem to adapt poorly to polymorphic systems with
explicit type arguments. Consider inference for a term M [A] with expected type B. We would like
to compute an expected type for M, but cannot do so directly from A and B.
   We address this problem by introducing an explicit representation of unknown polymorphism.
The type [A]B denotes all polymorphic types ∀t.C such that C{A/t} is B. We generalize to arbitrary
sequences of implicit arguments, and introduce metavariables that stand in for sequence of implicit
arguments. Finally, we extend unification with rules that match known quantifiers against unknown
polymorphism. Returning to our motivating example, we can initially elaborate sel d k f x with
unknown instantiations following sel itself and each application. We then resolve these instantiation,
when solving unification and row constraints, giving the desired elaboration.
   Note that [−]− itself is a kind of “pseudotype” constructor, in that it has no introduction or
elimination rules, does not (uniquely) classify any terms, and never appears in a final elaborated
term or its typing. Instead, it exists only during type inference, to guide the generation and solving
of unification constraints.
   While our problem was motivated by the interaction between qualified types and first-class
polymorphism, our solution is more general. By disconnecting the insertion of implicit arguments
from their determination, we allow more flexible uses of first-class polymorphism while providing
for a modular and (relatively) simple implementation. One essential challenge of type inference
for first-class implicit polymorphism is that the same source term may have multiple valid but
incompatible elaborations. As we will show (§6), ATIA makes it possible to defer the choice between
elaborations until later in type inference, without losing the ability to apply sensible defaults in
cases where there is genuinely an unforced choice.

2.4     Comparison with Related Approaches
There have been many proposals of type inference algorithms for first-class implicit polymorphism.
Before plunging into the technical presentation of yet another such, we want to contrast our
approach with two other proposals.
   QuickLook [25] is the approach currently implemented in GHC. Haskell is an ornate language,
with many mostly orthogonal type system features and much syntactic sugar. One of QuickLook’s
design goals is to impact as little as possible of the rest of the type system, and so minimize the
change to the compiler. QuickLook’s designers highlight that its implementation changed only
1% of GHC’s type inference mechanism. ATIA, in contrast, involves a fundamental change to the
structure of types used during type inference, and impacts the inference rules for all elimination
forms. Nevertheless, our experience suggests that this change is not unmanageable (§8). Our
treatment of elimination forms is uniform and so can itself be abstracted. Moreover, we did not
need special handling of unknown polymorphism in simplifying constraints arising from row types
or higher-order unification.
   Haskell is the most widely used language to use qualified types, and QuickLook is a constraint-
based algorithm. However, Haskell’s type class constraints and type families specifically exclude
polymorphic types, a restriction that has not been lifted by any of GHC’s many extensions. Therefore,
the specific motivation for our work, in which domain-specific constraint solving discovers that
terms have polymorphic types, does not arise for QuickLook.
   Kovács has developed several type inference algorithms for first-class implicit polymorphism,
including FCIF [10] (first-class implicit functions) and DOE [11] (dynamic order of elaboration).
Dependent types are an explicit goal of Kovács’s systems, whereas we have not considered whether
or how ATIA would extend to dependent types. There are two significant differences between
our approach and those of Kovács. First, we have a constraint-based system, whereas his systems
perform unification and insertion as part of a single bi-directional traversal. Supporting separate

3   Language
We begin by introducing our surface and elaborated languages. Their syntax is given in Figure 1.
The elaborated language is the subset of the surface language in which all type abstraction and
application are explicit and all term abstractions have type annotations. This subset is enforced
by a typing judgment, described later in this section. Note that the surface language allows both
implicit and explicit type abstraction and type application.

  Types. We distinguish types A from pseudotypes P. Types contain the usual constructs: type
variables t, quantified types ∀t.A, and functions A → B (standing in for arbitrary type constructors).
The extension of ATIA to higher-kinded types is routine and orthogonal to the goals of this paper.

  Pseudotypes. Pseudotypes extend types with metavariables α and unknown polymorphism [S]P.
Metavariables represent unknown types during type inference. Metavariables are annotated with
kinding environments Δ, used to avoid variable escape. We will reject attempts to assign type
A to metavariable α Δ unless the type variables of A are included in Δ. The pseudotype [S]P
captures all polymorphic types that give P when instantiated with the sequence of types S. For
example, [A :: B :: •] (A → B) corresponds to any of ∀tu.t → u, ∀tu.A → u, ∀tu.t → B, and
∀tu.A → B. Sequences of types may be terminated by a sequence metavariable ι, representing
potential instantiations, or with the empty sequence •. For example, [ι]A → A corresponds to both
∀t.t → t, in which case we must have that ι ↦→ A :: •, or to A → A, in which case we must have
that ι ↦→ •. We will write P :: S for the sequence beginning with the Ps and continuing with S.

   Terms. Terms M are mostly standard, and include both pre- and post-elaboration terms. We
allow function abstraction both with and without type annotation, but will not allow the latter
post-elaboration. Type application M [S] uses sequences of types, not individual types, to support
inferring unknown instantiations. Outside type inference, these can be viewed simply as iterated
type application. We will assume that the input to type inference does not contain any metavariables,
that is, that type annotations are proper types A and that type applications are of the form M [A :: •].

4   Traversal
ATIA has two stages. In the first, described in this section, we traverse the syntax of a term,
generating both an elaborated term and a set of unification constraints. In the second, described in
the next section, we (hopefully) solve the generated constraints. Unlike many constraint-based type
inference systems, however, the expressiveness of our system depends on intertwining traversal
and constraint solving.
   Traversal is described by the judgment Δ; Ψ; Θ1 ⊢ M : P ↩→ N ⊣ Θ2 , given in Figure 4. Intuitively,
traversal has five inputs—a kind environment Δ, a pseudotype environment Ψ, a set of constraints
Θ1 , a term M, and an expected pseudotype P—and generates two outputs—an elaborated term N ,

                                Proc. ACM Program. Lang., Vol. 10, No. ICFP, Article 304. Publication date: August 2026.

and an expanded set of constraints Θ2 . We will always have that Θ2 implies Θ1 (more formally
described by Lemma 6). In the style of Algorithm M and of Pottier and Rémy [23], but in contrast
to many other type inference systems, we treat the expected type always as an input to type
inference, and never have inferred types as an output. However, as the expected type may contain
metavariables, we do not enforce information flow as bidirectional approaches do.
   At a high level, we divide our traversal rules into three categories. Introduction steps correspond
to the introduction of some type former, directed either by the term itself or by its expected type.
Introduction steps restrict the expected type; for example, typing an abstraction λx.M only makes
sense if the expected type is a function type A → B. This restriction will appear as a new input
constraint in subderivations. Elimination steps correspond to the elimination of some type former.
Elimination steps build the expected types of their subterms from their expected type. Elimination
steps also provide the opportunity for implicit instantiation. Simplification steps manipulate the
constraint set, or use the input constraints to transform the type inference problem. We will describe
the rules in each category in turn. As a running example, we will infer the type of auto (λx.x) true,
where auto : (∀a.a → a) → (∀a.a → a) = λx.x x and true : ∀b.b → b → b = λx y.x.

4.1     Introduction Steps
Rule (i-tlam) checks explicit type abstractions, and establishes the form of introduction rules. We
elaborate the body M to N in an environment that additionally binds type variable t. The expected
type of the body is a new metavariable β, but with the additional constraint that the expected type
P unifies with ∀t.β. (We will always use β for new metavariables.) As Θ2 entails Θ1 , this constraint
propagates to the output of (i-tlam).
   Our implementation attempts to solve the unification constraint P = ∀t.α eagerly. This has two
benefits. First, should the expected type not have a quantifier at its head, we can immediately report
a type error. Second, should the expected type have a quantifier at its head, we may also acquire
additional type expectation for the body. To simplify this presentation, we have separated eager
unification into rules (i-simpl,i-subst), which we describe later in this section (§4.3). Nevertheless,
the role of eager unification is emphasized by constraints being added to the inputs above the line,
not to the outputs below it.
   Rule (i-forall) inserts implicit type abstractions, guided by the expected type. If the term M is
not a type abstraction, but the expected type is a quantified type ∀t.P, we introduce type variable t
in the context and correspondingly add a type abstraction Λt in the elaborated term. We assume
that the quantified variable t is fresh; our implementation uses de Bruijn indices, and so freshness
of variables is not a concern. We apply rule (i-forall) eagerly; the other rules should all be read
as having the side condition that the expected type P is not quantified. Because (i-forall) only
inserts type abstractions based on the expected type, the introduction of type abstractions is still

4.2   Elimination Steps
Rule (i-var) checks variables, and establishes the form of elimination rules. While the variable
rule is not an elimination rule in declarative type systems, in systems with implicits it frequently
corresponds to elimination of implicit arguments, as it does for us. Correspondingly, we elaborate
variable x to the implicit application x [ι]. Here ι is a new metavariable, to be instantiated with
a (potentially empty) sequence of instantiations. We look up the actual type of x, P, and require
that P instantiated with ι unify with the expected type Q. Note that, like Pottier and Rémy [23]
but unlike most presentations of type inference, our variable rule does not do any instantiation
directly. Instead, the potential for instantiation is all deferred to solving the generated constraint.
   Rule (i-app) checks applications. At its heart, the rule here is the same as in Algorithm M: to
check an application with expected type P, we check the function with expected type β → P and the

type of the function, in which the codomain [ι]P includes unknown polymorphism. Second, we
want the function’s domain type—specifically, first-class polymorphism in the domain type—to
influence type checking the argument. This is accomplished by threading the output constraints Θ2

case, the input term is a β-redex (Λt.M) [A], and in such a case it seems clear we should not
introduce new (implicit) type arguments between (Λt.M) and A.

5.1   Consistent Extension
We define constraint solving in terms of consistent extension Θ ⊕ C. If C is α Δ = P, and Θ includes
α Δ = P1, . . . , α Δ = Pn , then Θ ⊕ C = Θ, C, P = P1, . . . , P = Pn if, and only if:
    1. α Δ does not appear in P;
    2. the free type variables of P all appear in Δ;
    3. if there is any equation β Δ = Q or ι Δ = S in Θ, then neither β Δ nor ι Δ appears in P.
                                       ′          ′                              ′      ′


Condition 1 is the occurs check, which avoids inferring infinite types. Condition 2 ensures that
type variables do not escape their binders. Condition 3 guarantee that the constraint set does not
become circular. We require parallel conditions if C is ι Δ = S. Finally, if C is P = Q, where neither P
nor Q is a metavariable, then Θ ⊕ C = Θ, C. When consistent extension appears on the right-hand
side of a simplification or guessing rule, we treat the rule as having an implicit side condition that
the consistent extension is defined.
   For example, consider the constraint set ε, α → α = t → u. Rule (c-arr) says that this set
should step to ε ⊕ α = t ⊕ α = u. The first extension gives the constraint set ε, α = t, and the
second gives ε, α = t, α = u, t = u. But this constraint set is unsatisfiable, as t = u cannot be
simplified. Or, consider the constraint set ε, α → (α → α) = t → (u → u). This constraint set
can be simplified to ε, α = t, α → α = u → u. If we apply rule (c-arr) immediately, we arrive at
ε, α = t, α = u, t = u, and the final constraint cannot be simplified. We can apply rule (c-subst),
giving ε, α = t, t → t = u → u, and then (c-arr) giving ε, α = t, t = u, t = u, but neither of the latter
two constraints can be further simplified, and this constraint set is also unsatisfiable.

5.2   Simplification Rules
We now describe the individual simplification rules. Rules (c-arr) and (c-all) decompose equalities
on arrow types and quantified types. In (c-all), we assume that the two types have the same
quantified variable; our implementation uses de Bruijn indices for type variables, and so this
condition is trivially met. Rules (c-reflt ,c-reflα ,c-reflι ) discharge reflexive equalities. Rule (c-
subst) applies results in Θ to the constraint C.
   The constraint [•]P = Q requires that, after doing no instantiation of Q, P and Q unify. This is
captured by rule (c-empty). The constraint [P :: S]Q1 = Q2 gives a concrete set of instantiations P
for Q2 , captured by rule (c-seq). The remainder S will either be •, in which case (c-empty) applies,
or a metavariable ι Δ .
   The final three simplification rules actually solve for implicit polymorphism, and have similar
structure. Consider a constraint [ι Δ ]Q1 = ∀t.Q2 . This corresponds to implicit polymorphism in the
source program: some term has polymorphic type ∀t.Q2 , and we have opportunity ι Δ to instantiate
its parameters. How should we do so?
   In some cases, the answer is immediate. For example, suppose we have the constraint [ι Δ ] (t →
t) = ∀u.u → u (where we assume that t is in Δ). That is: some term has type ∀u.u → u, and we
must instantiate this term to match the type t → t. The only possible solution is to instantiate
u to t, which we capture by instantiating ι to the sequence t :: •, leaving the trivial constraint
t → t = t → t.
   Other cases are not so simple. Suppose we have the constraint [ι 1Δ ] [ι 2Δ ]P = ∀t.Q. That is, we have
a term with polymorphic type and two possible instantiations of it. We no longer have a unique
solution. We can instantiate the ts either at ι 1 , at ι 2 , or even split between them, and nothing in this
constraint forces our hand. Or, consider [ι Δ ]α Δ = ∀t.P. Now, depending on the eventual solution of
α, we may need to instantiate more or fewer of the t at ι.
   Rules (c-impl,c-no-impl,c-impl-seq) handle the cases in which the instantiation is forced. In
rule (c-impl), we require that Q1 is neither a metavariable nor further polymorphic instantiation;

                               Proc. ACM Program. Lang., Vol. 10, No. ICFP, Article 304. Publication date: August 2026.
304:14                                                                                     J. Garrett Morris


thus, it must be a type variable, arrow, or quantifier. In this case, we instantiate the first quantifier
with a fresh metavariable β Δ and introduce a fresh sequence metavariable ι 2Δ to account for any
more quantifiers in Q2 . In rule (c-impl-seq), we have one unknown instantiation followed by a
series of known instantiations, but then can be sure that no more instantiations are possible. We
divide the available quantifiers between the two sources of instantiation. In rule (c-no-impl) we
have no quantifiers and so no implicit applications are possible.

variables, which seems to be generally consistent with programmer expectation and is also the

6.2     Record Types
This section presents a greatly simplified version of the row type system that originally motivated
the development of ATIA. The significant addition is qualified types, which extend the language of
types with (domain-specific) constraints restricting the instantiation of type variables. Qualified
types have two significant interactions with ATIA. First, constraints are introduced and eliminated
implicitly, and so the extended system has to account for multiple kinds of implicit abstraction
and instantiation. Second, these constraints may themselves introduce new type equalities during
simplification, adding additional sources of implicit polymorphism.
   Our original motivation, the Rω language [7], uses row types to capture the structure of extensible
records and variants, and manipulates row types using several row-specific constraints. For this
example, we will limit ourselves to considering just records and only one constraint over records.
In Rω, satisfied constraints are witnessed by evidence, which in turn contributes to the semantics of
operations on extensible records and variants. As the semantics of these operations are orthogonal
to the challenges of first-class implicit polymorphism, we will omit evidence.

7    Metatheory
We sketch the argument that ATIA (unextended) is sound—that is, that if type inference succeeds,
the resulting term is well-typed in the elaborated language. We will write T for the set of types, P for
the set of pseudotypes, A for the set of metavariables, and I for the set of sequence metavariables.
  Our key challenge is relating the pseudotypes introduced during type inference to their eventual
solutions. We define a relation on pseudotypes P  Q which holds when either P and Q are the
same type or when one of them is a pseudotype that includes the other. For example, we have both
that ∀t.t → t  [A :: •] (A → A) and that ∀t.t → A  [A :: •] (A → A).
    Definition 1. Define  ⊆ P × P to be the closure of the rules

                                         [S]P  Q{P ′ /t}
                                        [P ′ :: S]P  ∀t.Q        [•]P  P
under reflexivity, symmetry, transitivity, congruence, and α-equivalence.
   We relate constraint sets Θ to substitutions. We begin by restricting our attention to constraint
sets that can arise from type inference.
  Definition 2. Θ is consistent if and only if there is an ordering of its equations C1, C2, . . . , Cn such
that Θ = ε ⊕ C1 ⊕ C2 ⊕ · · · ⊕ Cn .
   Let substitutions σ range over A ⇀ T × I ⇀ T ★, and define the action of σ on terms Mσ, on
pseudotypes Pσ, and on pseudotype environments Ψσ as expected. We use fuv(P) ⊆ A ∪ I for the
free metavariables and sequence metavariables in P, and extend as expected to terms, constraints,
and environments. We write dom(σ) ⊆ A ∪ I for the domain of definition of the components of σ.
  Definition 3. We say σ models Θ, σ |= Θ, if and only if fuv(Θ) ⊆ dom(σ) and, for every P = Q ∈ Θ,
Pσ  Qσ.
This is a standard definition of the modeling relationship, extended to account for pseudotypes.
  We establish sufficient conditions for a constraint set to have a model.
    Lemma 4. If Θ is consistent and reduced, then there is some σ |= Θ.
The argument is by induction on the ordering of equations C1, C2, . . . , Cn guaranteed by consistency

σ such that σ |= Θ′ . By repeated application of Lemma 6, σ |= Θ. By Lemma 8, Δ; Ψσˆ ⊢ N σˆ : P ˆ    σ.
   ATIA is terminating by standard arguments. The traversal phase is structurally recursive, except
for simplification steps. Simplification is an extension of typical descriptions of unification by
equations [1], and the same arguments for termination apply.

We have built an experimental implementation of ATIA in Haskell, as part of an implementation of
the Rω row type system [7]. This section provides some observations of that implementation.

   Rω adds significant complexity to the type inference problem. Rω is built on top of Fω, and so
introduces both type normalization and higher-order unification. Row types themselves introduce
new problems in unification—for example, rows admit various forms of permutation. Rω also
supports mapping type functions across rows and has a relative complement operator on rows. All
of these add to the complexity of normalization and unification. Our implementation also supports
generalization of local definitions, which introduces its own complexities in the flow of constraints
and treatment of type variables.
   Much of Rω’s row typing is captured with constraints on row types rather than in the structure
of row types themselves. These constraints add complexity to our solver. Solving these constraints
may refine metavariables—our motivation for revisiting the problems of first-class polymorphism.
   Despite this, our implementation remains (relatively) small and
simply structured. Figure 10 reports lines of code (excluding com- File                     SLOC

   One source of concern about ATIA is the extent to which the handling of implicit polymorphism
leaks into other aspects of type checking and predicate simplification. Our experience suggests
that there is very little overlap between the implementation of implicit polymorphism and other
features. Concretely, simplification of the various row predicates includes no special handling of
implicit polymorphism. Metavariable refinements arising from row predicates may refer to implicit
polymorphism, but solving those refinements is entirely modular.
   Another concern is reporting type errors. In general, constraint-based approaches may make it
more difficult to report type errors, as errors may not be discovered while traversing terms. Our
implementation makes little attempt to track whence constraints arise, but systems like GHC show
that this need not be a problem in practice. More significantly, unsolvable constraints may contain
unknown polymorphism pseudotypes. Two unpleasant options are immediately available. On the
one hand, pseudotypes can be suppressed when reporting errors. This simplifies the programmer’s
view, but may provide an incomplete view of the actual error. On the other, pseudotypes may
be reported. This requires programmers to understand their role. A better option would be to
report the potential of instantiating types without displaying pseudotypes directly. We suspect that
resolving these problems would be necessary for wide deployment of ATIA.

    All four approaches reject benchmark A8a. This benchmark essentially involves “floating” type
quantifiers: auto2 has type ∀b.(∀a.a → a) → b → b, but to align with id it needs to have type
(∀a.a → a) → (∀b.b → b). FCIF and DOE reject this term because moving implicit arguments is

otherwise argument x will not be given polymorphic type.

speculate that our approach may scale to inferring some polymorphic argument types (§11.2).

other systems accept this term without type annotation. For us, the problem is in the order of
arguments. We insert type abstraction as guided by the expected type of a term, and the expectation
of polymorphism in this cases arises from ids. We demonstrate this with benchmark C5c, which
only changes the order of arguments, and which we accept without type annotation.
    We reject E1 for the same reason we rejected A8, as it requires permuting the order of quantifiers
and function arrows. We even reject its η-expansion, as the type of k does not force the result of
h x to be polymorphic, and so we do not insert an an implicit type abstraction.
    Overall, these benchmarks show that our approach is competitive with the state of the art. The
most significant weakness demonstrated in our approach is in the insertion of type abstractions, as
it is driven only by the type information present during traversal. This is demonstrated by C5: a
programmer might reasonably be surprised that C5c is accepted without type annotation whereas
C5a is not. We think this is an important area of future work (§11.1). Nevertheless, particularly
given the flexibility of our system to accommodate predicate solving features absent from other
implementations of first-class polymorphism, we think these are positive results.

10     Related Work
There have been many proposals for extending Hindley-Milner type inference to first-class implicit
polymorphism, with different expressiveness-to-complexity ratios. We summarize some of those
most relevant to our work.
    Jones [9] gives one of the first accounts of first-class implicit polymorphism. His approach wraps
polymorphic values in data constructors, providing clear boundaries for when polymorphism is
introduced and eliminated, and has been adopted in Haskell among other languages. Emrich et al.
[3, 4] describe an approach in which variables x can be “frozen” ⌈x⌉, preserving their polymorphic
types, and are fully instantiated otherwise. In their system, generalization happens at let-bindings,
but any term M can be wrapped in let x = M in ⌈x⌉ to give it its principal polymorphic type.
These systems rely on syntactic boundaries to introduce or eliminate polymorphism, whereas we
introduce type abstractions and applications implicitly, based on type information.
    Botlan and Rémy [2] define MLF , which matches the expressiveness of System F with fully
implicit type annotation and application. Parreaux et al. [21] propose a significant generalization
of MLF , F { ≤ } , and a corresponding type inference algorithm SuperF. SuperF accepts every example
in Figure 12. MLF and F { ≤ } rely on bounded polymorphism (below for MLF , above and below for
F { ≤ } ), where the bounds capture required instantiations. In typing example B1, they conclude
a type like ∀abc.Nat → b ≤ a, Bool → c ≤ a ⇒ a → Pair b c. To paraphrase Parreaux et al.
[21]: rather than conclude a parametric polymorphic type directly, they rely on intersection-based
subtyping. The resulting type system has very different expressiveness from System F, and so we
view the type inference problem as essentially different from ours. Lam et al. [12] describe a further
extension, in which bounds are treated as constraints (with evidence) in a qualified type system.
This system could serve as a unification of our work with the generality of bounded quantification,
while preserving an underlying System F-like semantics.
    Leijen [14, 15] propose progressive simplifications of MLF called HMF and HML, but at a not
insignificant expressiveness cost. For example, because HMF maintains principal types, the term
single id (benchmark C4) can only be given the type ∀a.List (a → a), not also List (∀a.a → a).
    GHC has seen several approaches to first-class implicit polymorphism, including Boxy Types
[27], FPH [28], and more recently Guarded Instantiation [26] and QuickLook [25]. QuickLook
is expressive, and its implementation is local to the treatment of application spines. However,
QuickLook is less expressive than our approach in some cases, such as the Church-encoded variants
of benchmarks C6b (without a type annotation) and C8. Moreover, QuickLook’s treatment of
application spines can be complex, including requiring rechecking arguments.
    Kovács [10, 11] gives two impressively expressive systems, FCIF and DOE. These systems in-
corporate unification and insertion within a single bi-directional type checking pass, rather than
separating constraint solving. We do not know how well they would adapt to incorporating domain-
specific constraint languages, as motivates our approach. Otherwise, our approaches seem roughly
comparable in expressiveness.

11     Future Work
We have presented an expressive and modular approach to type inference with first-class implicit
polymorphism. We conclude by identifying two particularly promising areas of future work.

11.1     Inserting Type Abstractions
A guiding principle of our approach is that we must be able to delay the insertion of type application
to constraint solving. However, we do not have the same flexibility with type abstractions. Implicit
type abstractions are inserted by rule (i-forall) based on the expected type present during traversal.

Proc. ACM Program. Lang., Vol. 10, No. ICFP, Article 304. Publication date: August 2026.
Another Type Inference Algorithm for First-Class Implicit Polymorphism                                          304:27


If this type is refined later to be polymorphic, it will be too late to insert type abstraction. This
inexpressiveness appears in benchmark E2: by the time that l forces the instantiation of k to be
∀a.Nat → a → a, we have already failed to add a type abstraction around λx.h x.
   It is tempting to wonder if we cannot replay our approach to unknown instantiation by adding
unknown generalization in types as well. The pseudotype ⟨ι 1 ⟩P, for example, might represent an
unknown generalization of P. Simplifying ⟨ι 1 ⟩α 1 → α 1 = ∀t.t → t would instantiate ι 1 to the
argument sequence t :: • and α 1 to t, introducing the corresponding type abstraction.
   The most significant challenge we see here is the interaction between potential generalizations
and variable escape. In the example above, if α 1 appears outside the term typed by ⟨ι 1 ⟩α 1 → α 1 , then
the proposed solution would result in leaking the Λ-bound variable t. With the current treatment,
where the all Λs are known at traversal time, it is also easy to track the legal instantiations of
metavariables. With unknown generalizations, it may be less so.

11.2    Inferring Polymorphic Types
Consider the term λf .pairnb (f zero) (f true) where zero : Nat, true : Bool, and pairnb : Nat →
Bool → Pair Nat Bool. The challenge in type inference for this term is discovering that f must have
the polymorphic type ∀a.a → a. Neither our approach, nor QL, FCIF, or DOE rise to this challenge.
For us, traversal gives:
             ε ⊢ λf .pairnb (f zero) (f true) : α 1 ↩→
                   λf :α 2 .pairnb (f [ι 1 ] zero [ι 2 ]) (f [ι 3 ] true [ι 4 ]) ⊣
                   α 1 = α 2 → Pair Nat Bool, [ι 1 ] (Nat → [ι 2 ]Nat) = [ι 3 ] (Bool → [ι 4 ]Bool)
We have simplified and substituted the result term and constraint set, and have treated the types
Nat, Bool, and Pair as opaque to limit irrelevant instantiations.
    From this point, we go wrong. As neither [ι 1 ] (Nat → [ι 2 ]Nat) nor [ι 3 ] (Bool → [ι 4 ]Bool) are
quantified types, (c-impl-no) concludes that ι 1 = • and ι 3 = •, leaving the obviously unsatisfiable
constraint (Nat → [ι 2 ]Nat) = (Bool → [ι 4 ]Bool).
    It is tempting, however, to observe that other solutions to this constraint set exist. In particular,
if we consider the constraints α 2 = [ι 1 ] (Nat → [ι 2 ]Nat) and α 2 = [ι 3 ] (Bool → [ι 4 ]Bool) together,
then it even seems plausible that we could generate the solution α 2 = ∀t.t → t by antiunifica-
tion, and that, having found it, the constraint set ∀t.t → t = [ι 1 ] (Nat → [ι 2 ]Nat), ∀t.t → t =
[ι 3 ] (Bool → [ι 4 ]Bool) would simplify and give rise to a correct elaborated term.
    Introducing antiunification for constraints [ι 1 ]P = [ι 2 ]Q should be conservative with respect to
our current algorithm. Currently, this constraint solves if and only if P = Q, and in that case the
least general antiunification of P and Q will be P. On the other hand, we would want to rule out
misbehaviors like solving α 1 = [ι 1 ]Nat, α 1 = [ι 2 ]Bool with α 1 = ∀a.a. There would also be some
engineering effort in detecting opportunities for antiunification, as we might eagerly substitute
when we discover the first solution. Nevertheless, we think this demonstrates a significant potential
benefit to our approach, and hope to explore it more thoroughly.
